1. Objetivo y alcance

Este documento registra el proceso de publicación de StockVelia como aplicación web accesible por internet. Se describen las plataformas utilizadas, las configuraciones que pueden identificarse en las capturas y el estado funcional informado durante las pruebas. Las capturas sirven como evidencia de las pantallas de configuración de Vercel y Render; no se recibieron capturas del panel de Supabase.

StockVelia es una aplicación web de gestión de inventarios orientada a pequeños negocios, como tiendas, minimercados y misceláneas. Su arquitectura separa la interfaz, la lógica del servidor y el almacenamiento de datos.

2. Arquitectura desplegada y estructura del proyecto

Flujo general de las solicitudes: el navegador carga la aplicación publicada en Vercel; el frontend envía solicitudes a la API alojada en Render; el backend procesa la operación y consulta o modifica los datos almacenados en PostgreSQL en Supabase. La respuesta vuelve al frontend para actualizar la interfaz.

Capa Plataforma Tecnología Rol en el despliegue
Frontend Vercel React Publica la interfaz que utiliza el usuario.
Backend Render Node.js + Express Ejecuta el servidor y expone los endpoints de la API.
Base de datos Supabase PostgreSQL Administra la base de datos PostgreSQL utilizada por el backend.

2.1 Repositorio y estructura tipo monorepo

En la pantalla de importación de Vercel se observa la cuenta de GitHub conectada (jaiderovalle6) y el repositorio StockVelia (rama main). Vercel detecta más de una aplicación dentro del repositorio, organizada en carpetas separadas para backend (Express, /api) y frontend (Create React App, /).

Esta estructura corresponde a un repositorio con más de una aplicación (estructura tipo monorepo). Para publicar cada parte de manera independiente, se configura la carpeta raíz correspondiente en cada plataforma.

4.3 Consideración sobre el directorio raíz y plan

Como el repositorio contiene carpetas backend y frontend, Render debe ejecutar los comandos en la carpeta que contiene el package.json del servidor. Si el package.json del backend está dentro de backend, el Root Directory del servicio debe apuntar a esa carpeta, o los comandos deben ajustarse para ejecutarse desde la raíz del repositorio. 5. Base de datos en Supabase y variables de entorno

Supabase se utiliza para alojar la base de datos PostgreSQL de StockVelia. El backend de Render debe conectarse a esa base de datos mediante los parámetros o la cadena de conexión configurados como variables de entorno.

5.1 Pasos generales de configuración en Supabase

  1. Crear o seleccionar el proyecto de StockVelia en Supabase.
  2. Utilizar la base de datos PostgreSQL asociada al proyecto.
  3. Obtener los parámetros de conexión desde la sección de conexión de la base de datos.
  4. Configurar esos datos en las variables de entorno privadas del backend en Render.
  5. Comprobar desde el backend que puede conectarse y ejecutar consultas sobre PostgreSQL.

Nota sobre evidencias: No se recibieron capturas del panel de Supabase, por lo que no se especifican el nombre del proyecto, región, método de conexión, tablas ni valores de configuración. Esos datos deben añadirse cuando se disponga de las capturas o de la configuración exacta.

6.1 Incidente de recuperación de contraseña (SMTP en Render Free)

Al probar la recuperación de contraseña, los registros (logs) de Render mostraron los siguientes mensajes: 

Error al solicitar recuperación: connect ENETUNREACH 2607:f8b0:4001:c62::6d:587 - Local (:::0)
Error al solicitar recuperación: Connection timeout

El backend utiliza Nodemailer y la cuenta Gmail stockvelia7@gmail.com para conectarse a smtp.gmail.com. La configuración original utilizaba el puerto 465 con secure: true. Posteriormente se probó el puerto 587 con secure: false y family: 4 para forzar IPv4.

El error ENETUNREACH indica que no se pudo alcanzar la dirección de red. El timeout indica que la conexión no se completó dentro del tiempo permitido. Render documenta restricciones de SMTP saliente en los servicios gratuitos para los puertos 25, 465 y 587. Por ello, cambiar de puerto o forzar IPv4 no elimina una restricción de red del plan.

6.2 Alternativas evaluadas

  • Mantener Render Free y usar un proveedor de correo mediante API HTTPS, como Resend. Para enviar correos a cualquier usuario desde un remitente propio en producción se debe verificar un dominio.
  • Utilizar un servicio de Render de pago que permita SMTP saliente y conservar Nodemailer con Gmail, verificando previamente el plan y los precios vigentes.
  • La dirección Gmail stockvelia7@gmail.com puede seguir siendo la cuenta de correo del proyecto, pero la decisión técnica depende del servicio de envío y de las restricciones del alojamiento.

7. Seguridad, lista de verificación y datos pendientes

7.1 Seguridad y buenas prácticas

  • No guardar contraseñas, claves API ni cadenas de conexión en el repositorio.
  • Excluir los archivos .env mediante .gitignore.
  • Configurar las variables secretas directamente en Render y las variables públicas necesarias en Vercel.
  • No exponer credenciales de Supabase ni secretos JWT en el frontend.
  • Permitir mediante CORS únicamente los orígenes necesarios.
  • Revisar los logs de Render sin imprimir tokens, contraseñas ni datos privados.
  • Después de modificar variables de entorno, volver a desplegar el servicio correspondiente.
