Plan de respaldo y recuperación de StockVelia

Lineamientos de copia de seguridad, retención, restauración y contingencia para la base de datos PostgreSQL, archivos de perfil/avatar y configuración del sistema multi-empresa.

Sistema: StockVelia Multi-Empresa BD Crítica: PostgreSQL (Stock, Movimientos, Auditoría) Archivos: Avatares y Configuración Actualización: 23 de noviembre de 2026

Secciones

  • 1. Alcance y activos críticos
  • 2. Objetivos RPO / RTO y frecuencia
  • 3. Procedimientos de respaldo
  • 4. Procedimientos de restauración
  • 5. Verificación, seguridad y riesgos

1. Alcance y clasificación de activos críticos

El plan de respaldo de StockVelia protege la información operativa, contable de inventario y de seguridad de todas las empresas registradas en la plataforma, garantizando que el borrado lógico (estado = 'INACTIVO' en productos y estado = 'ELIMINADO' en usuarios), la revocación de sesiones (tokens_blacklist) y el historial de movimientos_inventario y auditoria puedan recuperarse sin inconsistencias.

Activo / Dominio Criticidad Componentes incluidos en el respaldo
Base de datos transaccional PostgreSQL Crítica Tablas roles, empresa, usuario, usuario_empresa, categorias, productos, movimientos_inventario, codigos_recuperacion, tokens_blacklist y auditoria, además de funciones, restricciones CHECK y el trigger trg_actualizar_stock.
Archivos de usuario y medios Media Fotografías/avatares cargados vía POST /api/usuarios/perfil/foto (JPG, JPEG, PNG y WEBP hasta 2 MB), manteniendo coherencia con las rutas almacenadas en el perfil de cada usuario.
Configuración y código fuente Alta Repositorio de Backend (Node.js/Express), Frontend (React) y plantillas de configuración/entorno (sin exponer secretos en claro dentro de respaldos no cifrados).

2. Objetivos RPO / RTO, periodicidad y retención

Los objetivos de punto de recuperación (RPO) y tiempo de recuperación (RTO) se definen según el impacto operativo de cada componente:

Activo RPO objetivo RTO objetivo Frecuencia de respaldo y retención sugerida
Base de datos PostgreSQL <= 24 h (o menor con WAL/incrementales) <= 2 horas Respaldo lógico diario automatizado (pg_dump) con retención mínima de 7 copias diarias, 4 semanales y 3 mensuales.
Archivos de avatar / adjuntos <= 24 horas <= 2 horas Copia sincronizada diaria del directorio de uploads junto con el respaldo diario de aplicación/BD, reteniendo 14 días.
Código y configuración Inmediato (por commit / release) <= 1 hora Control de versiones en Git y respaldo de configuración cifrada en cada liberación o cambio de infraestructura.

3. Procedimientos de respaldo

Pasos operativos estándar para generar copias consistentes sin interrumpir el servicio ni comprometer la integridad de stock:

  • Respaldo lógico de PostgreSQL: Ejecutar pg_dump en formato personalizado (-Fc) o SQL con transacción consistente para capturar esquema, trigger trg_actualizar_stock, restricciones y datos de todas las empresas.
  • Empaquetado de archivos de perfil: Archivar de forma periódica la carpeta de imágenes de perfil de usuarios, evitando archivos residuales tras el reemplazo de avatar en POST /api/usuarios/perfil/foto.
  • Aislamiento y almacenamiento externo: Transferir cada copia a una ubicación distinta al servidor principal (almacenamiento en nube o equipo externo) y verificar que el archivo resultante no esté vacío ni corrupto.

4. Procedimientos de restauración y contingencia

Secuencia de actuación ante corrupción de datos, error humano masivo o caída de instancia:

  • 1. Contención y diagnóstico: Pausar escrituras o aislar el tráfico hacia la instancia afectada si existe corrupción de datos, identificando la fecha/hora exacta del incidente y el respaldo íntegro más cercano.
  • 2. Restauración en entorno aislado o de recuperación: Restaurar el volcado de PostgreSQL (pg_restore) y los archivos de avatar correspondientes, verificando que los roles (1, 2, 3), empresas, productos y movimientos_inventario queden consistentes.
  • 3. Validación de integridad de stock y sesiones: Comprobar que el stock de los productos coincida con los movimientos registrados y que el estado de usuarios (ACTIVO, INACTIVO, ELIMINADO) y bloqueos temporales no presenten inconsistencias.
  • 4. Reanudación y registro en auditoría: Habilitar nuevamente el acceso de usuarios, notificar al equipo responsable y registrar el evento de contingencia/recuperación.

5. Pruebas de restauración, seguridad y riesgos

Controles periódicos para asegurar que las copias de respaldo sean confiables cuando se necesiten:

  • Simulacros de restauración: Ejecutar al menos una prueba de restauración en un entorno de pruebas (staging/local) para confirmar que el respaldo levanta sin errores de permisos, extensiones ni dependencias.
  • Cifrado y control de acceso a respaldos: Proteger los archivos de respaldo y variables sensibles (JWT_SECRET, credenciales de BD y correo SMTP) mediante cifrado y acceso restringido exclusivamente a personal autorizado.
Riesgo operativo a considerar: Restaurar una base de datos de un punto anterior sobrescribe movimientos recientes y estados de sesión/tokens posteriores a ese instante; por ello, siempre debe comunicarse el corte temporal a los Propietarios y Administradores Operativos de las empresas afectadas.
