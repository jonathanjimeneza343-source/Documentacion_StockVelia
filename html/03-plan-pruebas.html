1. Estrategia y alcance del plan de pruebas

Este plan define cómo verificar que StockVelia cumple los requisitos funcionales, reglas de negocio y requisitos no funcionales en su estado real de implementación (backend Node.js/Express, base de datos PostgreSQL con triggers y restricciones CHECK, y frontend React con sincronización periódica cada 15000 ms).

1.1 Niveles y tipos de prueba

  • Pruebas funcionales (API + UI): Validan registro/vinculación multi-empresa, login, bloqueo tras 5 intentos fallidos, recuperación de contraseña con código de 6 dígitos, cierre de sesión con revocación en tokens_blacklist, CRUD de categorías y productos, movimientos de inventario (ENTRADA, SALIDA/VENTA, BAJA), administración de usuarios y reportes.
  • Pruebas de autorización y multi-tenancy (RBAC + Aislamiento): Verifican restricciones por rol (Propietario = 1, Administrador Operativo = 2, Empleado = 3) y el rechazo (403 Forbidden) ante accesos cruzados entre empresas (id_empresa).
  • Pruebas de integridad de base de datos y concurrencia: Comprueban el trigger trg_actualizar_stock, transacciones BEGIN / COMMIT / ROLLBACK con FOR UPDATE, no negatividad de stock/precio/stock mínimo y exigencia de justificación en bajas/daños.
  • Pruebas de interfaz y exportación: Verifican filtros combinados en Catálogo, selector de empresa, tema dinámico por color corporativo, subida de avatar (JPG/JPEG/PNG/WEBP hasta 2 MB), refresco periódico y descarga de reportes en PDF y CSV.

2. Entorno de pruebas y datos semilla

Para ejecutar el plan de forma reproducible se requieren los siguientes componentes y conjuntos de datos:

Componente Configuración requerida para pruebas Datos y precondiciones
Backend API Servidor Node.js/Express activo con JWT_SECRET, configuración CORS y servicio de correo (SMTP/Nodemailer) disponible para pruebas de recuperación de contraseña. Rutas /api/auth, /api/usuarios, /api/categorias, /api/productos, /api/movimientos y /api/reportes operativas.
Base de Datos Instancia PostgreSQL con tablas roles, empresa, usuario, usuario_empresa, categorias, productos, movimientos_inventario, codigos_recuperacion, tokens_blacklist y auditoria, más trigger trg_actualizar_stock. Roles sembrados: 1 (Propietario), 2 (Administrador Operativo), 3 (Empleado). Dos empresas de prueba (Empresa A y Empresa B) para validar aislamiento multi-empresa.
Frontend React Aplicación React conectada al backend, con localStorage limpio al inicio de cada ciclo de sesión y navegador actualizado con soporte para IntersectionObserver y descarga de archivos. Usuarios activos de los tres roles en Empresa A y un Propietario vinculado a múltiples empresas.

3. Casos de prueba funcionales (CP-FUNC)

Matriz de casos de prueba principales agrupados por flujo del sistema:

ID Módulo / Flujo Pasos clave de ejecución Resultado esperado
CP-01 Registro y vinculación multi-empresa 1. Registrar una empresa nueva con correo inédito.
2. Registrar una segunda empresa usando el mismo correo de Propietario activo y su contraseña válida. 		Se crea la empresa, se asigna rol 1 (Propietario), se vincula en usuario_empresa, se habilita el selector de empresa y se registra la acción en auditoria.
CP-02 Login, bloqueo por 5 intentos y logout 1. Enviar 5 intentos consecutivos con contraseña incorrecta.
2. Intentar login en el 6.° intento.
3. Iniciar sesión con clave correcta y luego ejecutar logout. 		Tras el 5.° fallo se fija bloqueo_hasta por 15 minutos y se responde 423 Locked. Tras login válido, se emite JWT (2h) y limpia contador; tras logout, el token queda en tokens_blacklist y es rechazado con 401.
CP-03 Recuperación de contraseña 1. Solicitar código de recuperación para un correo válido.
2. Ingresar código de 6 dígitos vigente y nueva contraseña segura (mayúscula, minúscula, número, mín. 6 caracteres). 		Se envía el código con vigencia de 15 minutos; al restablecer se actualiza la contraseña con Bcrypt, se reinicia intentos_fallidos = 0, se limpia bloqueo_hasta y se invalida el código usado.
CP-04 Categorías y Productos 1. Crear categoría en Empresa A e intentar duplicar el nombre ignorando mayúsculas.
2. Crear producto con código único, precio >= 0, stock >= 0 y stock_minimo.
3. Dar de baja lógica un producto y probar eliminar una categoría con producto asociado. 		Se rechaza la categoría duplicada en la misma empresa; el producto queda ACTIVO; la baja lógica cambia el producto a estado = 'INACTIVO' conservando historial; eliminar categoría con productos asociados es bloqueado.
CP-05 Movimientos y actualización de stock 1. Registrar ENTRADA de 10 unidades.
2. Registrar SALIDA o BAJA superando el stock disponible.
3. Registrar BAJA o motivo de daño/obsolescencia sin justificación y luego con justificación válida. 		La ENTRADA incrementa el stock vía trg_actualizar_stock y alerta si stock <= stock_minimo. El exceso de salida/baja y la falta de justificación en bajas/daños son rechazados; con justificación válida se registra y actualiza stock.
CP-06 Usuarios, perfil y color corporativo 1. Propietario crea Administrador Operativo y Empleado.
2. Propietario cambia color_tema de la empresa.
3. Usuario sube avatar válido (PNG/WEBP <= 2 MB) y prueba archivo inválido (> 2 MB o formato no permitido). 		Se aplican los permisos por rol, cambia el color corporativo en la UI, se guarda el avatar eliminando el anterior y se rechazan archivos fuera de formato o tamaño máximo.
CP-07 Reportes, filtros y exportación 1. Filtrar catálogo por texto, categoría, estado de stock y rango de precios.
2. Filtrar movimientos por fechas y producto en Reportes y exportar a PDF y CSV. 		Los filtros y totales (unidades y valoración stock * precio) coinciden con los datos activos de la empresa y generan archivos descargables en PDF y CSV (UTF-8 con BOM y separador ;).

4. Pruebas de seguridad, concurrencia y base de datos

Escenarios críticos para validar que las protecciones técnicas funcionan bajo condiciones exigentes:

  • Aislamiento multi-empresa (CP-SEC-01): Con un token de Empresa A, invocar endpoints de reportes o intentar operar sobre recursos de Empresa B. Debe retornar 403 Forbidden sin exponer ni alterar datos de Empresa B.
  • Control de acceso basado en roles (CP-SEC-02): Verificar que un Empleado (rol 3) no acceda a gestión de usuarios ni reportes en la UI ni pueda editar/desactivar productos en la API, y que un Administrador Operativo (rol 2) no pueda gestionar al Propietario ni crear otros Administradores Operativos.
  • Concurrencia en movimientos de stock (CP-CONC-01): Lanzar solicitudes simultáneas de SALIDA/BAJA sobre un mismo producto con stock limitado. Gracias a la transacción y al bloqueo de fila FOR UPDATE más la validación de stock no negativo, nunca debe producirse stock negativo ni pérdida silenciosa de actualizaciones.
  • Restricciones SQL y refresco periódico (CP-BD-01): Verificar restricciones CHECK de precios y stocks no negativos y chk_justificacion_baja en PostgreSQL, así como la actualización en vistas tras operaciones y mediante refresco cada 15000 ms.

5. Criterios de salida, defectos y riesgos

Condiciones necesarias para dar por aprobado el ciclo de pruebas y riesgos operativos a monitorear:

5.1 Criterios de entrada y salida

  • Criterio de entrada: Entorno desplegado, migraciones/esquema PostgreSQL aplicados y datos semilla cargados.
  • Criterio de salida: 100% de los casos críticos (autenticación, bloqueo de 5 intentos, multi-empresa, roles, movimientos de stock, justificación de bajas y reportes) ejecutados sin defectos abiertos de severidad Crítica o Alta.
Riesgos clave a vigilar: Desincronización de reloj o zona horaria entre servidor y PostgreSQL al evaluar bloqueo_hasta y expiración de códigos de recuperación (15 min), o fallos en el envío de correos SMTP en entornos de prueba sin credenciales externas configuradas.
